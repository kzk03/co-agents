# co-agents

AI に開発を任せるときの「判断」(誰が決めるか)の研究の作業ディレクトリ。

2026-11-21 に、それまでのコード、出力、データを削除し、パイロットからやり直している。方向は下の案で、教授と確認中。

## 1. 研究の方向(案)

### 題目

コーディングエージェントの対話ログから、人間に残す判断を定め、抽出する(Human.md の基準と生成)

### 背景

- AGENTS.md / CLAUDE.md のように、エージェントの振る舞いを自然言語で定めるファイル(定義ファイル)が広く使われている。
- エージェントに任せても、人間が判断すべき事項がある(承認、公開、削除、費用、リスクの許容など)。それを Human.md として別に管理する考え方がある。
- しかし、Human.md に**何を、どう書くべきか**の基準は無い。それを作る方法も無い。

### これまでに分かったこと(旧分析。LLM による判定で、人手の確認はない。見当としてだけ使う)

- 定義ファイルには、人間の判断が必要な記述がほとんど無い(規則の 1% 程度)。あっても「承認を得てから」「頼まれない限り commit しない」のように文面に明示されているので、定義ファイルから切り出すこと自体は難しくない。
- 人間の判断は、定義ファイルではなく対話の中に現れる。却下、中断、「commit はまだ」「先に自分で試させて」といった発話である。人が行為を止めた 23 件のうち、対応する規則が定義ファイルにあったのは 0 件だった。
- 人は「次から聞かずに済むよう CLAUDE.md に書いて」とも頼む(255 件)。ただし、書かれる中身はほぼ「エージェントが自分で守る規則」(委任)で、「以後も人間が決める」(留保)という形ではほとんど残らない。
- したがって、**抽出元は定義ファイルではなく対話ログ**にする。

### 目的

1. **定める**: Human.md に書くべき判断とは何か、どう書くかの基準を、実際の介入をもとに定める。
2. **抽出する**: 対話ログから、その基準に沿って判断を抽出し、Human.md を作る手法を作る。
3. **評価する**: 抽出の精度と、実際の運用での有用性を示す。

```
対話ログ(却下・中断・押し返し・「CLAUDE.md に書いて」)
   │
   ├─① 定める:人が実際に止めた・決めた・書かせた判断から、Human.md の型と書式を作る
   │
   ├─② 抽出する:①の基準に沿って、ログから判断を抜き出す
   │      ├─ 留保(以後も人間が決める)  → Human.md
   │      └─ 委任(決めた内容を任せる) → CLAUDE.md / AGENTS.md
   │
   └─③ 評価する:人手の正解との一致、後の介入や追記を先取りできるか
```

### リサーチクエスチョン

- **RQ1(定める)**: Human.md に書くべき判断とは何か。実際の介入から、型と書式を定める。
- **RQ2(抽出)**: 対話ログから、RQ1 の基準に沿った判断をどの程度の精度で抽出できるか。
- **RQ3(有用性)**: 抽出した Human.md は、その後のセッションでの介入や、人が後から定義ファイルに足した規則を、どれだけ先取りできるか。

### Human.md の 1 項目の書式(叩き台)

| 欄 | 内容 | 例 |
|---|---|---|
| 何を | 対象の行為 | commit、push |
| どんなときに | 条件 | 動作を確かめる前 |
| 誰が決めるか | 人に聞く / 任せる | 人に聞く |
| どう確認するか | 事前に承認 / 止まって報告 など | 実行前に承認を得る |
| 根拠 | 元になった対話 | セッション id と発話 |

書かないもの:
- エージェントだけで守れる手順(CLAUDE.md 側に書く)
- 毎回その場で決める内容の判断(事前に書けない)

### 評価の考え方

- **小規模な正解**: 人手 2 名で、対話ログの判断に注釈する。
- **大規模な自動評価(時系列での分割)**: ある時点までのログから抽出し、それより後に人が実際に定義ファイルに足した規則や、後の却下・押し返しにどれだけ当たるかを見る。草案の合成データの役割(大規模な評価)を、実データで置き換える。
- **再実行による評価はしない**: 当時のリポジトリの状態を再現できないため。

### 既存研究との差分

既存研究は「書かれた規則をエージェントが守れたか、効果があるか」を見ている。この研究は「誰が決めるか」を軸にし、人間に残す判断の基準を定めて抽出する。

| 研究 | 中身 | 見ていないもの |
|---|---|---|
| Tang ら「How Coding Agents Fail Their Users」(EMNLP 2026) | SWE-chat などの 20,574 セッションの押し返しから、エージェントのずれを分類。最多は明示的な規則の無視(38%) | その判断を人に残すべきだったか |
| Hedwig(CAIS 2026 デモ、arXiv 2605.11495) | 承認・却下の履歴から、行為ごとに確認するかを学習 | 書ける判断の基準。評価は合成の人物像のみ |
| TellOnce / TRACE(arXiv 2606.13174) | ユーザーの修正を規則や実行時の検査に変換する | 留保。すべてを委任として扱う |
| Personalized Skills(arXiv 2608.10319) | 開発者の履歴から SKILL.md を作り、再実行で評価 | 決定権 |
| Self-Improving Rules(arXiv 2607.13091) | 受け入れられたレビューを規則にして蓄積 | 誰が決める規則か |
| Agent READMEs(TOSEM 2026)など | 定義ファイルの中身の分類 | 実際の介入との照合 |

### データ

- **主**: SWE-chat(COLM 2026、Hugging Face `SALT-NLP/SWE-chat`、約 44GB)
  - 実際の開発者とエージェントの対話ログ。17,968 セッション、707 リポジトリ。約 7 割が Claude Code。
  - 作業中の承認、却下、中断が見える唯一の公開データ。
  - ほぼ個人開発で、1 つのリポジトリ(`entireio/cli`)に介入の 28% が集中している。
- **補助**: AIDev(MSR 2026、Hugging Face `hao-li/AIDev`)
  - エージェントが作った PR。チームのリポジトリの定義ファイルと比べるために使う。

## 2. やり直すときの注意

- 定義ファイルは、セッション当時の版で照合する。いまの版とは 7 割で違う。版は GitHub のコミット履歴から復元できる。
- `entireio/cli` を除いた値を必ず併記する。
- 正規表現や単語の一致による分類と照合は誤りが多い。最終的な判定は人が確かめる。
- 正解は人手 2 名で作る。LLM どうしの一致では足りない。

## 3. 最初のパイロット

1. SWE-chat を取り直し、定義ファイルのあるリポジトリから 30 セッションほどを抜き出す。
2. 人が読み、人間の判断が現れた場面に印を付ける。
   - Human.md に書くべきか
   - 留保か委任か
   - 何についての判断か
   - 書くならどう書くか
3. 次のことを確かめる。
   - 判断の定義と注釈の手順が成り立つか
   - 1 セッションあたり何件あるか
   - 書式の叩き台で書けるか
4. その結果で、RQ1 の基準と評価の設計を確定する。
