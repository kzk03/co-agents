### H028 | open-telemetry/opentelemetry-collector-contrib#48379 | src=issue
TITLE: [processor/schema] Add cache_ttl configuration option for in-memory schema cache
--- REQUEST ---
[ISSUE open-telemetry/opentelemetry-collector-contrib#48342 by MikeGoldsmith] feat(processor/schema): add cache TTL configuration option
### Component(s)

processor/schema

### Is your feature request related to a problem? Please describe.

The schema processor's in-memory cache (`CacheableProvider`) uses `cache.NoExpiration` — entries live forever for the process lifetime. This means:

- If a schema URL initially returns incorrect or empty content, the bad result is cached permanently until the collector restarts.
- If a schema file is updated on the server, the collector won't pick up the new version until restart.

### Describe the solution you'd like

Add a `cache_ttl` configuration option that controls how long successfully fetched schemas are kept in the cache before being re-fetched. The underlying `go-cache` library already supports TTL natively, so this should be a straightforward change for the in-memory layer.

```yaml
processors:
  schema:
    cache_ttl: 24h  # default: no expiration (current behavior)
    targets:
      - https://opentelemetry.io/schemas/1.26.0
```

#### Interaction with persistent storage (#48267)

When the optional storage extension is configured, the provider chain is: **in-memory cache → storage → HTTP**. A TTL on the in-memory cache alone is insufficient — when an in-memory entry expires, the `StorageProvider` returns the persisted schema before HTTP is reached, effectively making the TTL a periodic re-read from disk rather than a re-fetch from the server.

The implementation should ensure that when the in-memory TTL expires, the collector attempts an HTTP fetch rather than just reloading from storage. Storage should act as a fallback when HTTP fails (offline resilience), not as a permanent override that prevents re-fetching.

### Describe alternatives you've considered

- Restarting the collector to clear the cache — works but disruptive.
- No change — schemas rarely change in practice, but having a TTL provides a safety net for misconfigured URLs or updated schema files.
- TTL on in-memory only, accept that storage bypasses it — simpler but the TTL becomes meaningless when storage is configured.

### Additional context

Raised during review of #48267 (storage extension support).

The sensor should only return True when:

The sensor returns True even when no DAG runs exist within the execution_range, causing downstream tasks to proceed without the expected dependency being met.

### H086 | pytorch/pytorch#177388 | src=issue
TITLE: [aten][autograd] Add narrow_scatter operator with autograd and torch.compile support
--- REQUEST ---
[ISSUE pytorch/pytorch#177372 by Sanskaaar1] Add torch.narrow_scatter operator to complete the *_copy/*_scatter operator family.
### 🚀 The feature, motivation and pitch

### The feature, motivation and pitch

PyTorch currently has `narrow_copy` but lacks the corresponding `narrow_scatter` operator, breaking the pattern where every `*_copy` operation has a matching `*_scatter` operation:
- `slice_copy` / `slice_scatter` - exists
- `select_copy` / `select_scatter` - exists
- `narrow_copy` / `narrow_scatter` - missing

Without `narrow_scatter`, the functorch functionalization layer can't properly handle mutations through narrow views. Right now users have to use mutation-based workarounds that don't work with functorch:

```python
# Current workaround (not functional, incompatible with functorch)
result = input.clone()
result.narrow(dim, start, length).copy_(src)
```

I'd like to propose adding `torch.narrow_scatter(input, src, dim, start, length) -> Tensor` which scatters values from `src` into a narrow region of `input`:

```python
import torch

# Basic usage
x = torch.zeros(10)
src = torch.ones(5) * 2
result = torch.narrow_scatter(x, src, dim=0, start=2, length=5)
# tensor([0., 0., 2., 2., 2., 2., 2., 0., 0., 0.])

# Autograd support
x = torch.randn(10, 10, requires_grad=True)
src = torch.randn(5, 10, requires_grad=True)
result = torch.narrow_scatter(x, src, 0, 2, 5)
result.sum().backward()  # gradients computed correctly

# torch.compile support
@torch.compile
def fn(x, src):
    return torch.narrow_scatter(x, src, 0, 2, 5)
```

The implementation can delegate to `slice_scatter` since narrow is just slice with step=1:

```cpp
at::Tensor narrow_scatter_symint(..., SymInt start, SymInt length) {
  c10::SymInt end = start + length;
  return at::slice_scatter_symint(self, src, dim, start, end, 1);
}
```

This keeps the implementation minimal and reuses all existing `slice_scatter` optimizations.


### Alternatives

Users can work around this with `slice_scatter` directly:
```python
result = torch.slice_scatter(input, src, dim, start, start+length, 1)
```

However, this is less intuitive (requires computing `end = start + length`) and inconsistent with the `narrow_copy` naming convention.

The mutation-based workaround also exists but doesn't work with functorch:
```python
result = input.clone()
result.narrow(dim, start, length).copy_(src)
```

### H099 | DefinitelyTyped/DefinitelyTyped#75208 | src=issue
TITLE: [hotwired__turbo] Align types with the v8.0.23 implementation
--- REQUEST ---
[ISSUE DefinitelyTyped/DefinitelyTyped#75207 by myabc] [hotwired__turbo] `StreamMessage` and `BrowserAdapter` are declared as value exports but do not exist at runtime
🤖 _Drafted with agent assistance._

While auditing `types/hotwired__turbo` against the Turbo source (hotwired/turbo @ v8.0.23), I found two declarations that claim runtime values which `@hotwired/turbo` does not actually export:

- **`StreamMessage`** — declared as `export class StreamMessage` with a constructor and static members (`wrap`, `contentType`). Turbo only uses this class internally; it is not re-exported from `src/core/index.js` nor from the package entry point (`src/index.js`).
- **`BrowserAdapter`** — declared as `export class BrowserAdapter`; also internal-only (lives in `src/core/native/browser_adapter.js`, never re-exported).

I verified against the built `dist/turbo.es2017-esm.js` export list (32 exports) — neither name is present.

Consequence: the following compiles cleanly against our types but fails at runtime, because both imports resolve to `undefined`:

```ts
import { BrowserAdapter, StreamMessage } from "@hotwired/turbo";

const message = new StreamMessage(fragment); // TypeError at runtime
StreamMessage.wrap("<turbo-stream>…</turbo-stream>"); // TypeError at runtime
```

Our own `hotwired__turbo-tests.ts` exercises exactly these patterns (`new StreamMessage(...)`, `StreamMessage.wrap(...)`, importing `BrowserAdapter`), so the tests currently encode the phantom API.

Options I see:

1. **Demote to types-only.** Make `StreamMessage` and `BrowserAdapter` interfaces (plus a separate type for the statics if we want to keep describing them). Breaking for anyone value-importing them — but that code is already broken at runtime, so arguably this is the fix. The existing `adapter as BrowserAdapter` cast for `progressBar` access keeps working with an interface.
2. **Fix upstream first.** Propose that hotwired/turbo exports `StreamMessage` (and possibly `BrowserAdapter`). `renderStreamMessage()` accepts a `StreamMessage` and `StreamMessage.contentType` is useful for `Accept` headers, so a runtime export seems defensible. Our declarations would then become truthful as-is.
3. **Both**: demote now, restore the class declarations if/when upstream exports them.

Related context on alignment philosophy: https://github.com/DefinitelyTyped/DefinitelyTyped/pull/75196#discussion_r3509421777
