# コードブック v1(人間がレビューで止めた理由)

作成: 2026-10-21(codebook 担当)。LLM 用の英語版は `work/codebook/prompt_v1.md`(内容は同じ)。

## 0. v0 から何を変えたか

- v0 の H1〜H5 は「コードからは分からない」という印象でまとめていた。critic の指摘どおり、性質の違う3つが混ざっていた。
  - (a) **情報が足りない**:渡せば解ける。→ v1 の **K**
  - (b) **書かれていない規約・設計意図**:事前に書ける。AGENTS.md の守備範囲。→ v1 の **R**
  - (c) **権限・価値・責任の判断**:情報を全部渡しても、決める人が要る。→ v1 の **D**
- v1 では「何が足りなかったのか」を問う。足りなかったのは事実(K)か、一般的な規則(R)か、決める人(D)か。
- **inferable(yes/partial/no)は廃止する。** 「LLM が気づけたか」をコーダーの印象で付けるのをやめる。代わりに reproduce 担当が実測する値(人間のコメントを見せずに LLM にレビューさせ、同じ指摘が出たか:yes/partial/no)を、別の変数として付ける。v1 のコーダーは再現できるかどうかを判断しない。
- 新しい軸として **文書化可能性**(§3)を加える。
- **HUMANS.md 固有の領域**は次のように定義する:**D-dir + D-risk + K-priv + R-gov**。
  - K-pub と R-tech は、モデルと検索が強くなるか、AGENTS.md に書けば消える。だから HUMANS.md を作る根拠にならない。
  - R-gov は事前に書ける。ただし書く内容が「誰が決めるか」なので、AGENTS.md ではなく HUMANS.md に属する。

## 1. カテゴリ

| コード | 名前 | 定義 | critic の区分 |
|---|---|---|---|
| X | 理由なし | 手続き上の操作だけ(「bot に状態を伝えるため」「保留中のレビューを破棄」、本文が空) | — |
| C1 | 正しさ | バグ、後退、漏れ、**作者に渡された依頼・Issue の仕様を守っていない**、誰でも挙げる規範(ユーザーのデータを消さない) | — |
| C2 | 保守性 | 命名、重複、単一責務、スコープの膨張、関係ない変更、既存の仕組みを使え(コードを見れば分かるもの) | — |
| C3 | 付随物 | テスト、ドキュメント、changelog、コミットの書式 | — |
| M | 機械的 | CI の失敗やコンフリクトを伝えているだけ | — |
| K-pub | 公開されている事実 | 差分の外にある個別の事実で、原理的には取りに行ける(リンクされた Issue・PR・commit、過去の revert、外部システムやプラットフォームの公開仕様) | (a) |
| K-priv | 人間しか持たない事実 | 非公開のチャットや会議、顧客の障害、メンテナの頭の中にある計画や意図、自分の環境や運用で観測したこと | (a) のうち人間しか持てない分 |
| R-tech | 技術上の規約 | この PR を超えて使える一般的なルールや設計原則(ロジックの置き場所、「機能はプラグインで」、「生成コードは直接編集しない」、サポートするバージョン) | (b) |
| R-gov | ガバナンス上の規則 | 誰が決めるか・承認するか、貢献者が負う義務(承認手続き、AI 利用の申告、CLA、リリースや backport の方針、所有者) | (b)。ただし中身は「人間の権限」 |
| D-dir | 方向・範囲・価値の判断 | 妥当な選択肢の中からその場で選ぶ。何を作るか、どの設計にするか、そもそも必要か、UX・ゲームバランス・製品としての価値。**人間同士の合意がまだない**場合もここに入れる | (c) |
| D-risk | リスク・時期の判断 | リスクを受け入れるか、マージを保留するか、順序とタイミング(リリースまで待つ、依存 PR を先に、影響範囲が大きすぎる、証拠なしには受け入れない) | (c) |
| UNK | 判定不能 | | — |

**主カテゴリは1つ**だけ選ぶ。理由が複数あるときは、レビュアーが強調しているものを選ぶ(本文がインラインより優先。「must」などの明示的なブロック語があればそれ。なければ最初の実質的な指摘)。それと別の種類の理由がはっきりあれば、**副カテゴリを1つ**付けてよい。

参考:HUMANS.md の中身を数えるときだけ、**O(操作・資格情報・物理)**を足す。資格情報、アカウント、署名、実機、耳や手による確認など、人間しか実行できない「行為」のこと。レビューの理由には現れなかった(§6)。

## 2. 判定手順(上から順に当て、最初に YES になったところで止める)

```
0. 実質的な理由がない? ─────────────────────────────→ X
1. 差分・repo のコードや設定・作者に渡された依頼文・広く共有された工学の知識から
   有能なエンジニアなら挙げられる、変更そのものの性質か? ──→ C1/C2/C3/M
2. 作者が情報を全部持っていても残る「その場の決定」か?
   (選択肢から選ぶ/価値判断/範囲・要否/合意が未了/保留・時期・リスク受容)
       ├ 方向・範囲・価値 ───────────────────────────→ D-dir
       └ リスク・保留・順序 ──────────────────────────→ D-risk
3. この PR を超えて使える一般的な規則・規約・設計原則を持ち出しているか?
   (実際に書かれているかどうかは問わない)
       ├ 誰が決める・承認する/貢献者の義務 ─────────────→ R-gov
       └ 技術上の規約・設計原則 ───────────────────────→ R-tech
4. 差分の外にある個別の事実に依存しているか?
       ├ 公開されていて取りに行ける ───────────────────→ K-pub
       └ 人間しか持っていない ────────────────────────→ K-priv
5. ─────────────────────────────────────────────→ UNK
```

境界のルール:
- **規則か事実か**:今後の PR にも当てはまる形で述べていれば R。一度きりの事実なら K。
- **規則か決定か**:既にある規則を引いていれば R。この件についてその場で決めていれば D。
- **決定済みか未決か**:他の場所で既に下された決定を引用している(「PR #123 で意図的にそう決めた」)なら K-pub。決定がまだ出ていない(「方針を合意しているところ」)なら D-dir。
- **仕様違反か範囲の判断か**:依頼文に範囲が書いてあって、それを超えた場合は C1。依頼文に書いてなく、レビュアーがその場で範囲を決めた場合は D-dir。
- `@copilot` などエージェント宛ての指示は、その指示の背後にある理由でコードする。

## 3. 文書化可能性の軸(critic の RQ-C)

C・X・UNK 以外の件(K/R/D)には、次の2段階で値を付ける。

1. **書けたか(コーダーが判断)**:この PR が存在する前に、その理由を一般的な文として repo の文書に書けたか。
   - `could`:書けた(規則、規約、サポートするバージョンやプラットフォームの仕様のように変わりにくい事実)
   - `no`:その場でしか出てこない(この PR 固有の事情、進行中の作業、今の時期、一度きりの判断)
2. **書かれていたか(実際の文書で確かめる)**:PR の base commit 時点の README / CONTRIBUTING / AGENTS.md / CLAUDE.md / .github/copilot-instructions.md を取得して確かめる。取得手順は `work/codebook/fetch_docs.py`。
   - `written-repo`:repo の文書に書いてあった
   - `written-elsewhere`:レビュアーがリンクした、既存の外部文書や wiki に書いてあった
   - `could` / `no`:上の 1 の値をそのまま使う
   - `未確認`:repo を取得できなかった

注意:D は定義上ほぼ `no` になる。したがって「書けたか」は R/K/D の区分とほぼ重なる。情報として新しいのは「書かれていたか」のほう。

## 4. v0 との対応

考え方の上での対応:

| v0 | v1 で主に行く先 | 注 |
|---|---|---|
| C1 / C2 / C3 / M | C1 / C2 / C3 / M(同じ) | 依頼文違反は v1 では明示的に C1 |
| H1 人間の文脈 | K-pub(リンクされた PR・経緯)、K-priv(非公開の議論・計画)、D-dir(合意が未了) | Wang の Duplicate も K-pub |
| H2 方針・設計判断 | R-tech(一般的な設計原則)、D-dir(その場の選択)、C2(一般的な設計衛生) | v0 で最大の混合カテゴリ |
| H3 暗黙の前提 | K-pub(外部システムの仕様)、K-priv(顧客・自分の環境)、C1(互換性など誰でも挙げるもの) | |
| H4 プロセス・責任 | R-gov(手続き・義務)、D-risk(保留・順序)、X(手続き上のノイズ) | |
| H5 セキュリティ・権限 | C1(誰でも挙げる危険)、R-gov(権限の規則)、D-risk(リスク受容) | 標本内に v0 で H5 と判定された件はなかった |
| inferable | 廃止 → reproduce の実測値(別の変数) | |

実データでの対応(aidev と ghhuman の H 系と NOAGREE、計 70 件。v0 は3コーダーの多数決、v1 は私のコード。出力は `work/codebook/agree.py`):

## 7. 信頼性(私 vs sonnet、70件、`work/codebook/agree.py`)

- 9値:一致率 0.66、κ 0.60(aidev 0.58 / 0.47、ghhuman 0.70 / 0.66)
- 群(C/K/R/D/X):一致率 0.69、κ 0.58
- HUMANS.md 固有かどうか(D + K-priv + R-gov か、それ以外か):一致率 0.79、κ 0.55
