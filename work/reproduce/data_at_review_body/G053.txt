This PR adds comprehensive tests that reproduce the behavior described in issue #379, where eager queries using `eager_load` are not temporal when combined with `as_of`.

## Problem

When querying temporal models with `as_of`, inline joins via `eager_load` do not apply the `as_of` timestamp to associated models, resulting in non-temporal rows being joined. This means associated records reflect the latest state instead of the historical state at the given `as_of` time.

## Test Implementation

The new spec (`spec/chrono_model/time_machine/as_of_eager_loading_spec.rb`) uses existing temporal models from the shared test structure - `Bar` and `SubBar` - with a has_many/belongs_to relationship, and tests three scenarios:

### 1. Direct Association Loading (✅ Passes)
```ruby
SubBar.as_of(historical_timestamp).first.bar.name
```
Correctly returns the historical bar name.

### 2. Lazy Loading with `includes` (✅ Passes)  
```ruby
SubBar.as_of(historical_timestamp).includes(:bar).first.bar.name
```
Correctly returns the historical bar name using lazy loading.

### 3. Eager Loading with `eager_load` (⏳ Pending)
```ruby
SubBar.as_of(historical_timestamp).eager_load(:bar).first.bar.name
```
**Currently fails** - Returns `nil` because the eager join ignores the `as_of` timestamp and doesn't find a matching current record.

## Test Setup

- Leverages existing temporal tables and models from `spec/support/time_machine/structure.rb`
- Uses established test data timeline with `$t.subbar.ts[0]` when SubBar exists and Bar has historical state
- No additional table creation or model cleanup required
- Follows all project linting and style guidelines
- Located in `spec/chrono_model/time_machine/` to match project conventions

## Expected Behavior vs Current Behavior

The pending test demonstrates that while the first two loading strategies correctly respect the `as_of` timestamp, `eager_load` does not propagate the temporal context to joined tables. This test will automatically pass once the underlying issue is resolved.

## Validation

- All existing specs continue to pass, confirming no regressions
- The new spec follows established patterns from `spec/chrono_model/time_machine/`
- Code passes all linting requirements with appropriate rubocop configurations

This spec serves as both documentation of the current limitation and a guard test that will validate the fix when issue #379 is addressed.
