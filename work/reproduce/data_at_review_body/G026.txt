The `struct-tag` rule was too opinionated about `validate` tag syntax, enforcing [go-playground/validator](https://pkg.go.dev/github.com/go-playground/validator/v10) syntax even when users might be using other validation libraries like [gookit/validate](https://github.com/gookit/validate) with different tag syntax.

This change adds the ability to disable specific tag checkers while keeping others enabled, providing granular control over struct tag validation.

## New Configuration Syntax

Users can now disable specific tag checkers using the `disabled` keyword:

```toml
[rule.struct-tag]
arguments = ["validate,disabled"]  # Disable validate tag checking
```

Multiple checkers can be disabled:

```toml
[rule.struct-tag]
arguments = ["validate,disabled", "toml,disabled"]
```

This can be combined with existing custom options:

```toml
[rule.struct-tag]
arguments = [
  "validate,disabled",      # Disable validate checking
  "json,custom_option",     # Add custom JSON option
  "bson,outline,gnu"        # Add custom BSON options
]
```

## Example

Before this change, using gookit/validate syntax would produce errors:

```go
type Foo struct {
    Version    int    `validate:"gt:0"`                                      // ❌ unknown option "gt:0"
    FooType    string `validate:"in:FOO,BAR,BAZ"`                            // ❌ unknown option "in:FOO"
    FooBarName string `validate:"required_if:enableFooBar,true|max_len:255"` // ❌ unknown option "required_if:enableFooBar"
    Name       string `validate:"min_len:1|max_len:256"`                     // ❌ unknown option "min_len:1"
}
```

With `validate,disabled` configuration:

```go
type Foo struct {
    Version    int    `validate:"gt:0"`                                      // ✅ ignored
    FooType    string `validate:"in:FOO,BAR,BAZ"`                            // ✅ ignored
    FooBarName string `validate:"required_if:enableFooBar,true|max_len:255"` // ✅ ignored
    Name       string `validate:"min_len:1|max_len:256"`                     // ✅ ignored
    JSONField  string `json:"field,invalid_option"`                          // ❌ still validates other tags
}
```

## Backward Compatibility

This change is fully backward compatible. Existing configurations continue to work unchanged, and all tag checkers remain enabled by default when no configuration is provided.
